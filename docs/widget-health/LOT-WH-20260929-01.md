## 5. 15-month UI reveal audit

**There is no 15-month reveal in code or docs.** The only month-based UI is `MonthlyPulseWidget`, and it was broken (F1).

| Month | Actual unlock |
|---|---|
| 1–12 | One dismissible text line per month (Usership only). No feature unlocks. |
| 13–15 | Clamped to the "Month 12" text (`MonthlyPulseWidget.tsx:123-126`). |

Everything else unlocks by **level and achievements**, not time (`interfaceEvolution.ts:198-225`): customThemes L5, widgetArrange L10, intentionHistory L15, exportData L25, narrativeReflection L30 and depth 0.66, plus dimension-based gates. `featureUnlockLevel` (0–5) is computed but never consumed. Roughly 45 widgets in the paid layout are always mounted with no tenure gate, and some self-gate inside.

**Gating bugs:**
- Month cap is 12, not 15.
- Month rounding uses `dayjs().diff('month')` in local time. Month-end joins (Jan 31) roll late.
- Pulse dismissal is per-device localStorage, so it re-shows on a new device.
- `daysSinceStart` depends on log sort order (`System.tsx:252`).
- Tenure anchors differ: `joinedAt` (widget) vs `createdAt` (`public-api.ts:1159`) vs `joinedAt || createdAt` (`:1256`).

**Recommended:** one `tenureMonth(user)` helper (anchor `joinedAt ?? createdAt`, UTC), a month-to-widget map for months 1–15, and a gate in System.tsx. Product decision needed on which widgets unlock in which month, so none was invented here.

## 8. Data log of widget usage — recommended spec

There is no cross-widget usage data today (W1). A minimal design that fits the doctrine:

- Client helper `logWidgetUse(widget, action)` batching into a single `widget_usage` Log event per minute. Fields: widget, action (view, interact, dismiss), dwell ms, mount ms (from `WidgetErrorBoundary` timings), and route.
- Server: whitelist `widget_usage` and add it to `/api/stats` as a per-widget count. Feed the aggregate to the QIE.
- Retention: raw Log, plus a daily roll-up.
- Show it to the user as their own log line, in keeping with the transparency principle.
