## 1. Widget wiring & data storage

**Pattern.** `System.tsx` (≈1,070 lines) composes widgets in stacks, each stack under `<WidgetErrorBoundary name=…>`: Memory, Game, Subscribe, MonthlyPulse, Recipe, Pulse, Context, Bioethics, Check-in, Self-care, Intentions, Community, Planning, Cosmic Update, Quantum Sign, Flash Drive, Investor, Quantum Engine Connect, Biofield Engine, Dashboard, Architect, Stats, Calendar, Benchmark.

**Data containers vs. displays** (from grep of API / store / localStorage usage):

| Class | Widgets |
|---|---|
| **Container** (writes data) | EmotionalCheckIn, SelfCareMoments (7 LS refs, Log post), IntentionsWidget (6 LS), CalendarWidget (Log `calendar_entry`), PlannerWidget (Log `plan_set`), RecipeWidget, MemoryWidget (answers → Log), ContextualPromptsWidget (direct `axios.post('/api/logs')`), QuantumSignWidget (4 LS), MonthlyPulse (3 LS) |
| **Display** (read-only derived) | Narrative, GoalJourney, PatternInsights, CorrelatedIndexes, QuantumState, SignalStream, Evolution, InterfaceEvolution, Interventions, ChatCatalyst, SystemPulse, UserMetrics, Benchmark, Architect |
| **Mixed / interactive** | MicroGame (988 LOC, 43 sound refs), MicroCalculator, MicroImage, CohortConnect, Time |

**Findings**
- **W-1 (med)** `ContextualPromptsWidget.tsx:232` bypasses `useCreateLog` and calls `axios.post('/api/logs')` directly → the `/api/logs` query cache is not invalidated by the same path as other widgets; entries may appear only after the 5-min `staleTime`. Unify on `useCreateLog`.
- **W-2 (low)** Unwrapped at top level: `TimeWidget` + `QuantumRandomWidget` (`System.tsx:444,616-617`) sit outside any boundary. Low risk (tiny, 146/81 LOC) but they are the first thing rendered.
- **W-3 (low)** `Block` label strings are duplicated between the two `isPaidAccount` layouts (`System.tsx` 428–520 vs 576–620, and `Breathe`/`Live` at 509/813). Drift risk; extract a shared header.
- **W-4 (info)** Event vocabulary written to Log is tiny: `calendar_entry`, `plan_set`, `self_care_skip`, `self_care_complete` (+ recipe). 40+ widgets leave no trace.

## 2. Wiring with LOT® AI, System tab, Portrait

- LOT® AI engine layer: `server/utils/ai-engines.ts` (Anthropic / OpenAI-compatible / others behind one interface). Widgets feed AI through **logs** (the only shared bus): `useLogContext` (CQGS Bioethics hook: timePhase, streaks, session depth, directives) is consumed for the Bioethics stack; server side reads the same logs via `getLogContext`.
- System tab is the single mount point; **Portrait** (`PublicProfile.tsx`, profile visits, `MonthlyPulseWidget`, `CosmicUpdateWidget`) reads `profile`/`metadata` rather than widget state. So Portrait sees **only what has been logged**. Because of W-4, most widget activity never reaches Portrait or AI.
- **W-5 (med)** Non-paid users get a reduced layout that skips AI widgets entirely (`System.tsx:414`). Intentional ("no AI, just essentials"), but it means the monk-style transparency/self-care loop is paid-only. Worth a decision.

## 3. Wiring with QIE, Memory, Story

- Memory: `MemoryWidget` (2 mounts: lines 521 and 965, different layouts, both boundary-wrapped) → `/api` memory endpoints → `server/utils/memory/*` (question-generator, trait-extraction, cohort-determination, pacing, **story-generator**). `generateMemoryStory(user, logs)` is imported by `api.ts:38`; weekly `lot_ai_story` surfaced via `api.ts:1129`.
- QIE: `QuantumEngineWidgets.tsx` is the only widget group using **LazyMount** (viewport-deferred subscriptions) — correct pattern.
- **W-6 (low)** Story generation consumes `logs`; since `/api/logs` has "no LIMIT" (comment in `queries.ts:136`) the server story/summary paths and the client `useLogs` both scale linearly with account age. This is the main long-run lag/size risk (see §6).

## 4. Context sync → Log ("military communications" model)

Today: weather, time, users-online live in `stores` and are rendered in the header `Block`s; the Log entry for a widget action contains only its own payload — **no environment snapshot**.

**Proposed SITREP-style entry** (not implemented — design for S-2 approval):

```
LOT-SITREP · 2026-10-11T03:40Z · W41 · Day 187
ENV   sky=clear t=18C  online=42/1,310  phase=night
WIDGET calendar_entry  src=CalendarWidget  ok
VITAL mood=calm energy=3/5  breathe=on
ACK   LOT® AI: received
```
Fields come from existing stores (`stores.weather`, `usersOnline`, `usersTotal`, `getCircadianPhase`). Implementation = one `buildSitrep()` helper merged into `useCreateLog` metadata; ~60 LOC, no schema change (`metadata` already JSON).

**Monk / pure-transparent lifestyle.** Suggested rules for LOT® AI: (1) one entry per intentional action, never per render; (2) every AI-visible datum is user-visible in the Log (no hidden widget state); (3) skip/ignore is logged as faithfully as completion (SelfCareMoments already does this — `self_care_skip`; extend the pattern).

## 5. 15-month month-to-month UI reveal

**Finding: no tenure-based schedule exists.** `grep` for 15-month / month-N logic: none. Reveal is driven by `interfaceEvolution.ts` (`visualRefinement` 0→1 from achievements/level/streak/entries) → `getLayoutDensity` thresholds 0.15 / 0.35 / 0.55 / 0.75 (breathable → comfortable → compact → dense → instrument) and `getFeatureUnlocks`. `System.tsx` itself only gates on paid tag and intention-engine hints.

Consequence: a heavy user can reach "instrument" density in month 2; a light user never leaves "breathable". If the intended product arc is 15 months of staged build-up, add a floor/ceiling: `monthIndex = clamp(monthsSince(firstLog),0,15)`, and cap `visualRefinement ≤ monthIndex/15` (earned **and** time-served). Suggested map for S-2 to confirm:

| Month | Reveal (proposal) |
|---|---|
| 1–2 | Header, Time, Memory, Check-in |
| 3–4 | + Self-care, Intentions, Recipe, Planner |
| 5–7 | + Pattern/Insights, Narrative, Goal Journey, Calendar |
| 8–10 | + Quantum Sign/State, Signal Stream, Cohort Connect |
| 11–13 | + Biofield engine, Correlated indexes, Evolution |
| 14–15 | + Dashboard, Architect, Benchmark; density "instrument" |

## 6. Loading speed

Production bundle (unminified-size listing from this build, `dist/client/js`): `app.js` **1.27 MB**, shared chunk `chunk-P5FIXEHD.js` **1.17 MB**, `chunk-MHN4ATKE.js` 348 KB, `about.js` 558 KB. 

- **L-1 (high)** All 46 widgets are **statically imported** into `System.tsx` (lines 30–81); zero `React.lazy` in the client. Only `QuantumEngineWidgets` defers *subscriptions* (LazyMount) — its code still ships in `app.js`. Converting below-the-fold stacks (Investor, Dashboard, Architect, Benchmark, Biofield, Flash Drive, Calendar) to `React.lazy` + `LazyMount` is the biggest first-load win, and fits the month-reveal model (code for month-11+ widgets need not load in month 1).
- **L-2 (high)** `utils/badges.ts` is ~7.6k lines and `SystemProgressWidget.tsx` 2,513 lines (mostly changelog string data, e.g. line 691/1024/1044) — static data in the main bundle. Move changelog/badge catalogs to lazy chunks or JSON fetched on demand.
- **L-3 (med)** `useLogs` fetches the full unbounded `/api/logs` (`queries.ts:134-136`); with ≥30 widgets reading it, one large response blocks every derived `useMemo`. Add server `limit`/`since` + a client windowed query for dashboards.
- **L-4 (low)** Build warns about duplicate object keys in `badges.ts` (e.g. `elixir_found` at 4825 and 6883): the later silently overrides the earlier.
- Existing good: `LazyMount`/`useInViewport` (200 px root margin), `useActiveViewport` pausing MicroGame loop off-screen, `React.memo` on `System`.

## 7. Lag test (code-path audit — not measured)

Existing instrumentation: `WidgetErrorBoundary` mount timer (warns >50 ms, `window.__LOT_WIDGET_PERF__`), `utils/perf.ts` INP + long-animation-frame observers (`window.__LOT_PERF__`).

- **Buttons/controls:** Sound/Radio toggle debounced 300 ms (`isSoundToggling`) — deliberate 300 ms dead-zone on rapid taps; acceptable, but a second tap inside it is silently ignored (no feedback).
- **Sounds:** `sound.ts` (652 lines) + Soviet chime/keyboard/game synth modules; `MicroGameWidget` has 43 sound refs. Audio contexts require user gesture; first-tap latency on iOS is the usual risk — verify on device.
- **Timers:** 9 intervals across widgets, all cleaned up; `SystemProgressWidget` has 3 setInterval/2 clear at the grep level but the extra match is a changelog string, not code → no leak.
- **Controls:** to actually measure, open the app and run `__LOT_WIDGET_LOG__.summary()` and `__LOT_PERF__.getEntries()` (both now/already exposed).

## 8. Widget usage data log — **implemented this push**

New `src/client/utils/widgetTelemetry.ts` (local-only, no network, privacy-safe):
- per widget: `mounts, errors, retries, interactions, lastMountMs, maxMountMs, slowMounts(>50ms), lastSeen`
- persisted to `localStorage['lot_widget_usage_v1']` (debounced 2 s, capped at 80 widgets, all storage access try/catch)
- console: `__LOT_WIDGET_LOG__.summary()`
- wired into `WidgetErrorBoundary`: records mount (with latency), error, retry → covers every boundary-named stack automatically.

Not yet done (next step): `interact` events per widget and a server roll-up so "usage across the LOT® platform" is aggregate, not per-device. Recommended: batch `getWidgetUsage()` to a new `/api/widget-usage` on `visibilitychange`, store in `metadata`, aggregate in admin-api.

## 9. Recommendations (priority order)

1. **Lazy-load** below-fold widget stacks + catalogs (L-1, L-2) — largest speed gain.
2. Add `limit/since` to `/api/logs` (L-3, W-6).
3. Decide 15-month time floor (§5) and implement as `visualRefinement` cap.
4. SITREP metadata on `useCreateLog` (§4); unify `ContextualPromptsWidget` on it (W-1).
5. Server roll-up of widget usage (§8).
6. Burn down the 104 TS errors, starting with duplicate keys / badge category types in `badges.ts`.
