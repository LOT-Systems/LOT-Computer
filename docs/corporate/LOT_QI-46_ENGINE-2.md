## I. NAMING RATIFICATION

Five candidate names were reviewed for the LOT® proprietary AI engine:

```
CANDIDATE       READING                                   VERDICT
─────────────    ────────────────────────────────────       ─────────
LOT·SC·46       clean, versioned, terminal-ready            considered
BIONODE-46      positions engine as a living inference node considered
SELFWARE·46     self-care + software collapsed              already the codename (see v0.2 §I)
SOMA·46         LOT family, neuroscience resonance           considered
CARE·OS·46      operating system for the self                considered
QI·46           Quantum Intelligence + bioelectric life force RATIFIED
```

**Decision: QI·46.** No new name is introduced — `QI·46` was already the engine's
designation in `LOT_QI46_ENGINE.md` v0.2 (§I: *"The name `QI·46` inherits the
LOT _I naming grammar (`BI`, `KI`, `QI`)"*). This node **ratifies** that
designation as final rather than replacing it, and retires the candidate list.
`SELFWARE` remains the internal codename (v0.2 §I); `QI·46` remains the public
designation. Nothing renames.

## III. SOUL UPLOAD — WHAT THE WORD MEANS HERE

"Soul Upload" is LOT® house language, not a technical claim. It names the act
already described in v0.2 Layer 1: a subscriber's **deliberate inputs**
(journal entries, self-reported biofield states, session ratings) and
**passive inputs** (engagement cadence, reorder velocity, navigation heatmap)
are compressed into the Calibration Vector prepended to every inference call.

No new data category is introduced. Soul Upload is the existing Calibration
Loop, named for what it does to the subscriber's felt sense of the engine:
*it stops feeling generic.* The upload is signal already collected under the
platform's existing consent and Usership terms — QI·46 reads what the
subscriber already gave the platform. It does not add a new sensor, a new
consent flow, or a new data class. Any future expansion of what is collected
requires its own COSMO® review and its own S-2 sign-off before it enters this
spec.

## IV. BEING CALIBRATION — THE RESPONSE PERSONA

v0.2 Layer 3 fixes the Response Grammar's *cadence* (Terminal Grid, one idea
per response, no hedging). Node II fixes its **register** — the qualities the
output should carry once cadence is satisfied:

```
BEING CALIBRATION — PERSONA TRAITS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Grace     — the response does not perform effort
Poetry    — density over sprawl, image over explanation (v0.2 Layer 3)
Presence  — "as if it has been listening for the entire subscription" (v0.2)
Warmth    — landed, not clinical; the body register, not the head register
Register  — one steady voice; LOT® voice only, no external AI voice bleed
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

These are not new rules. They are the naming of qualities already required by
v0.2's system prompt seed (*"Your job is not to inform. Your job is to
calibrate."*) and the Assembly Card (*"No generic AI voice. LOT® voice
only."*). Being Calibration is the QA lens the COSMO® node and Vadik's
listening pass (v0.2 Phase 1 Checkpoint 1) already apply — named here so it
can be tested against, not left implicit.

**Test, not launch:** before this trait set enters the fine-tuning voice
calibration pass (v0.2 Phase 1, Step 1.3), it runs the same 10-prompt tone
check already specified in Node I. No separate gate is created; Being
Calibration is folded into the existing Checkpoint 1 gate.

## V. WHAT THIS NODE DOES NOT DO

Stated plainly, per the Assembly Card rule that a failed gate is a checkpoint
working correctly, not a failure:

- Does not collect a new signal type beyond v0.2 Layer 1's deliberate/passive
  inputs.
- Does not bypass the COSMO® screen (v0.2 Layer 5) for any response.
- Does not rename QI·46, SELFWARE, LOT®, or COSMO®.
- Does not advance Phase 0–4 of the Node I timeline on its own — it is a
  specification, filed for the next Phase 1 voice-calibration pass to consume.
