## 1. SITREP — what was wrong with the foundation

| # | Finding | Severity | Effect |
|---|---|---|---|
| F1 | The widget read entries from `/api/logs`, which is capped at **500 rows**. | HIGH | After about 500 newer log rows, older calendar entries disappeared from the widget, including future dates. |
| F2 | `/api/logs` returns **only `note` events** for users with `hideActivityLogs`. | HIGH | Those users never saw any calendar entry they created. The widget looked broken. |
| F3 | Entries had no **time of day**. | MED | There was nothing to count down to or alert on. |
| F4 | Entries had no **status** (done/cancelled). | MED | Finished or cancelled items stayed in "upcoming" forever. |
| F5 | There were no notifications of any kind. | MED | The core requirement was missing. |

## 2. ACTIONS — what shipped

### 2.1 Data model (event-sourced in the Log, no migration)

Nothing is mutated in place. The current state is a fold over append-only Log rows, so the Log is a complete audit trail.

| Event | Metadata | Written by |
|---|---|---|
| `calendar_entry` | `entryId, date, time?, text, entryType` | Widget (`POST /api/logs`). Legacy rows without `entryId` use their log id. |
| `calendar_status` | `entryId, status: open\|done\|cancelled` | `POST /api/calendar/status` |
| `calendar_alert` | `entryId, stage: T-15\|T-0\|D-0` | `POST /api/calendar/alert` (idempotent) |

The fold and scheduler logic is in **`src/client/utils/calendar.ts`**. It is pure and has no side effects, so it can be unit-tested.

### 2.2 Server (`src/server/routes/api.ts`)
- `GET /api/calendar` returns only `calendar_*` rows (up to 3000, oldest first). It is not affected by the `/logs` cap or the `hideActivityLogs` filter. **Fixes F1 and F2.**
- `POST /api/calendar/status` validates `status`, looks up the entry, and writes a `calendar_status` row such as `[DONE] task: …`.
- `POST /api/calendar/alert` validates `stage`, `date` and `time`. It is **idempotent per (entry, stage)**: when several tabs or devices race to fire the same alert, only one Log row is written.
- `calendar_status` and `calendar_alert` were added to the `/logs` displayable events, so they appear in the Log tab.

### 2.3 Scheduler + alert overlay (`src/client/components/CalendarAlerts.tsx`)
- Mounted **once at the app root** (`entries/app.tsx`) inside a `WidgetErrorBoundary`. Alerts fire on every tab. The System tab unmounts when inactive, so the scheduler could not live inside the widget.
- Ticks every 15 s, and again when the tab becomes visible.
- Alert windows are bounded, so a stale tab never floods old alerts:

  | Stage | Applies to | Fires during |
  |---|---|---|
  | `T-15` | timed entries | from 15 min before the time until the time |
  | `T-0` | timed entries | from the time until 60 min after |
  | `D-0` | all-day entries | from 09:00 until the end of that day |

- When an alert fires, four things happen:
  1. A fixed signal card appears with a hard on/off blinking `■`, the stage, the time it fired, the type, the text and a date-time line (`SUN 15 NOV · 14:30`). It has **ACK** and **Done** buttons and stays until acknowledged. At most 3 cards are stacked, and a `T-0` card replaces the same entry's `T-15` card.
  2. A `calendar_alert` row is written to the Log.
  3. A system `Notification` is shown if the tab is hidden and permission was granted. Permission is requested only when the user creates a **timed** entry, from that click, which browsers require.
  4. A short two-pulse square-wave tone plays (880→1320 Hz, gain 0.05), only if the browser allows audio at that moment.
- Duplicate alerts are blocked at three levels: Log alert rows (server), then `localStorage` (`lot_calendar_fired_v1`, last 300 keys), then an in-memory set.
- `prefers-reduced-motion` turns off the blink and slide-in animations.

### 2.4 Widget (`src/client/components/CalendarWidget.tsx`). Same layout, a few additions
- Reads from `useCalendar()` instead of `useLogs()`.
- The header shows **`NEXT T-02:15`**, a countdown that updates every 30 s. It can also read `T-2D 04:15`, `T-3D`, `TODAY` or `NOW`. On the same day, a timed entry ranks ahead of an all-day entry.
- The add form has an optional **time** field (24h). Esc closes the form, text is limited to 500 characters, and double-submit is blocked while a save is in flight.
- Tapping a row shows **Done / Cancel**, or **Reopen** for closed entries. Notes cannot be marked done.
- Up to 3 **OVERDUE** open tasks or calls are listed above the upcoming items.
- The selected-day list shows times, completed items as `· DONE`, and cancelled items struck through. Cancelled entries no longer highlight their day in the grid.
- Rows wrap on narrow screens.

### 2.5 Log (`src/client/components/Logs.tsx`)
- The `CAL:`, `CAL-STAT:` and `CAL-ALRT:` blocks now show the stage or status and the type, the entry text, and a date-time line.

## 4. OPEN ITEMS / NEXT SESSION
1. **Not checked on a real phone yet.** In the bare harness at 390px, the existing month grid (7 × 2.5em) plus the label column overflows. The new rows and the add form now wrap. Still to do: check inside the real `Layout` on a phone and tighten the grid if it overflows there too.
2. **Alerts need an open tab.** Alerts fire only while some LOT tab is open. A service-worker or server push for closed tabs is the next step toward full reliability. The server could also use a scheduled job to write any missed `calendar_alert` rows.
3. **Lead time is fixed.** It is 15 min for every entry. A per-entry lead time (5/15/60) could be stored in metadata. The scheduler already reads everything from `computeDueAlerts`.
4. **12h display.** The UI is 24h on purpose (military date-time format). Decide whether to respect the `isTimeFormat12h` setting.
5. **No editing.** An entry's text, date or time can't be changed. The fix is to append a `calendar_update` event and fold it, in line with the event-sourcing model.
6. **No sound setting.** The alert tone has no user toggle yet. Consider linking it to the existing chime or sound settings.
