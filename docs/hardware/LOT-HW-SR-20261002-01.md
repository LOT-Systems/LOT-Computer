## 1. Product in one paragraph
A palm-size, two-part stainless-steel square (40 × 40 mm) that is a physical terminal of the LOT site.
The site (AI-driven) sends autonomous **pager-style notifications** ("Coffee time!") that appear on a small screen.
One side is mirror-polished steel. The other has a camera, a screen and one **COPY** button; pressing it sends a
signal back that appears in the **Log tab** of lot-systems.com. It samples weather/environment, charges wirelessly,
ships with PDF manuals, and is produced in a first run of **100 units** (PCBs via PCBWay).

## 3. Critical engineering risks (read first)
- **R1 — Thickness.** 40×40×5 mm total. Stack: display module ~2–3 mm, PCB 0.8, LiPo ≥3 mm, Qi coil 0.5–1, OV2640 module ≥4–5 mm, plus two 0.8–1 mm steel walls. Sum ≈ 12+ mm. EVT target **9–10 mm** with bare-FPC camera and 303040 cell; 5 mm only possible with no camera or a tiny CSP camera and a thin cell (small capacity). **Decision needed from Vadik.**
- **R2 — Wireless charging vs steel.** Stainless steel blocks/heats from Qi fields. The Qi coil must sit behind a **non-metal window** (ferrite sheet + glass/ceramic/PEEK disc inset in one steel part). Recommended: charge through the **front glass side** (device rests face-down on pad) — but then the polished side faces up, which is the nice display-case posture. Alternative: ceramic disc in the back plate.
- **R3 — Wi-Fi/BLE antenna vs steel.** A fully steel box is a Faraday cage. Put the antenna (FPC or u.FL + stick-on) directly under the glass window, away from steel by ≥3 mm, or use a 1.5 mm plastic slot in the frame. Needs RF test at DVT.
- **R4 — Polished steel + CNC at 100 pcs.** Mirror finish is a manual/chemical-polish step; expect scratches rejection ~10–20%. Order 120 sets.
- **R5 — Compliance.** Radio device: FCC/CE/UKCA, battery UN38.3, Qi certification. Not in the 100-unit budget (see §6); sell as "development units / limited art edition" first, with a certified module (ESP32-S3-WROOM-1 is pre-certified, which helps).
- **R6 — Power.** Always-on Wi-Fi drains a ~400 mAh cell in <1 day. Use deep sleep + periodic poll (30–60 s light-sleep) or a push channel; target ≥3 days.

## 4. Architecture
```
 LOT site (AI job) ──enqueue──▶ device_messages table ──▶ GET /api/device/messages (long-poll / SSE)
                                                              │
   [ESP32-S3] ◀── Wi-Fi ──────────────────────────────────────┘
     ├─ GC9A01/ST7789 screen  (notification text, 240×240)
     ├─ OV2640 camera         (snapshot on demand → POST /api/device/photo, v2)
     ├─ BME688 + VEML7700     (POST /api/device/telemetry every N min)
     ├─ COPY button (GPIO, wake source) ─▶ POST /api/device/event {type:"device_copy"} ─▶ Log tab
     └─ BQ51050B Qi RX + BQ25185 charger/path ── LiPo
```
**MCU:** ESP32-S3-WROOM-1-N16R8 (Wi-Fi 4 + BLE 5, native USB, DVP camera port, pre-certified).

## 5. LOT API connector (proposal, derived from the repo)
Current state in repo: user auth is cookie session (`config.jwt.cookieKey`, `src/server/routes/auth.ts`); user events are `Log`
rows (`fastify.models.Log.create({userId,event,text,metadata,context})`); the Log tab (`GET /logs`, `api.ts:1082`) only returns
events in the `displayableEvents` whitelist. There is no device auth today.

Proposed (new, not implemented yet):
| Endpoint | Purpose |
|---|---|
| `POST /api/device/pair` | Logged-in user gets one-time 8-char code; device exchanges it for a long-lived **device token** (hash stored server-side) |
| `GET /api/device/messages?since=` | Pager feed; returns `{id,text,priority,expiresAt}`; long-poll 25 s |
| `POST /api/device/ack` | Device confirms display (`id`, `shownAt`) |
| `POST /api/device/event` | `device_copy`, `device_boot`, `device_low_battery` → `Log.create` |
| `POST /api/device/telemetry` | T, RH, P, IAQ, lux, battery % → stored + optional `weather_update`-style log |
Auth: `Authorization: Bearer <device token>`, TLS only, rate-limited (reuse `config: { rateLimit }` pattern as in `/world/generate-element`).
**Doctrine hook (LOT-DOCTRINE "Backend Whitelist Hygiene"):** add `device_copy` (and other device events) to `displayableEvents`
in the same commit as the POST route, or the write→read loop silently breaks. What "Copy" copies (site's current focused text vs. last message)
is an open question (Q2).

## 9. Analysis — what is strong, what is weak
- **Strong:** ESP32-S3 + pre-certified module, off-the-shelf sensors, existing Log infrastructure means COPY → Log is ~1 route + 1 whitelist line.
- **Weak:** the steel enclosure fights wireless (RF + Qi) and the 5 mm height; polish yield; certification budget absent.
- **Cost driver:** steel body ($45) and BME688 ($15) ≈ 50% of BOM. BME280 swap saves ≈ $8 if gas AI is not essential.
- **Value check:** Is the camera necessary for v1? Dropping it saves ≈ $4 BOM and ~4 mm, and makes the 5 mm goal near-feasible.
