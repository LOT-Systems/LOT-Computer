## 2. Critical engineering risks (decide early)
- **R1 — 5 mm total height is extremely tight.** Stack: 0.6 mm steel wall ×2 + screen (~1.0–1.4) + PCB (0.8) + MCU/components (~1.0–2.4) + battery (≥3 mm) + Qi coil (~0.6) + camera (≥3–4 mm). Does not fit. **Recommendation:** 40×40×**8 mm** v1 ("5 mm" achievable only for the bezel/edge profile via chamfer, or by dropping camera/battery in a future "Lite"). Present 8 mm as the PVT target; keep a 6.5 mm stretch (thin 100 mAh cell, bare-die camera) as DVP-2.
- **R2 — Stainless blocks Qi and RF.** Eddy currents in steel kill wireless charging and detune Wi-Fi/BLE. Fix: charge **through the front** — front face includes a non-metal window (glass/ceramic/PEEK) over screen + coil + antenna; steel is only the polished back and the rim. Add ferrite sheet behind coil. Alternative: pogo/ magnetic charge contacts on the rim (cheap fallback).
- **R3 — Camera + screen + button on a sealed face** → thin glass window with printed bezel; button as sealed side/front dome or capacitive area. Water-resistance: IP54 target.
- **R4 — Push notifications on a battery device.** True push over Wi-Fi drains battery. Use MQTT/WebSocket with light-sleep (~10–20 mA avg too high for 150 mAh) → recommend **poll every 30–60 s with deep sleep** (days of life) plus optional "alert-now" via BLE phone relay later.
- **R5 — Compliance**: FCC/CE (radio module pre-certified helps), Qi, UN38.3 (battery shipping), RoHS. Budget for it before selling; internal 100-unit pilot is lower risk.

## 4. LOT API connector (proposed spec)
Auth: per-device token issued from the user's LOT account (device pairing code shown on screen → entered on lot-systems.com/os).

```
GET  /api/device/pull?since=<id>     → { notifications:[{id,text,kind,ts,ttl}], next:30 }
POST /api/device/event               ← { type:"copy"|"photo"|"battery"|"env", payload, ts }
                                       → writes a Log row, appears in the Log tab
POST /api/device/telemetry           ← { t,rh,p,gas_idx,lux,batt,rssi }
POST /api/device/photo               ← JPEG ≤ 200 KB (multipart)
POST /api/device/pair                ← { code } → { token }
```
- Notification generation: reuse existing AI engine (Anthropic client in `src/server`) with a scheduled job: pick short (≤ 60 chars) context-aware nudge ("Coffee time!") from user's OS state; enqueue per device.
- "Copy" button = marks the currently displayed notification/text as copied; `Log` entry `{source:"pager", action:"copy", text}`.
- Transport: HTTPS TLS 1.3 w/ cert pinning; JSON; OTA via `GET /api/device/firmware?ver=`.

## 5. PCBWay workflow
1. KiCad project in `hardware/pcb/` (outline 40×40, 4-layer, ENIG, 0.8 mm).
2. Gerbers + BOM (LCSC part numbers) + pick&place → PCBWay quote (PCB+ SMT assembly, "turnkey").
3. Stainless parts: STEP files → PCBWay CNC (316L, mirror polish Ra<0.1 on back) — request DFM review for 0.6 mm walls; alternative: MIM for >1k.
4. EVT 5 units first (~$600–1,000 incl. express), then DVT 20.
