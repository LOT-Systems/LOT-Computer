WHAT CHANGED:
- CalendarEntry gained an optional `time` (HH:mm) field, carried through the
  existing calendar_entry log event's metadata (backward compatible — entries
  without a time behave exactly as before).
- Add-entry form gained a native <input type="time"> beside the existing text
  field. No layout restructuring.
- A 1s tick (setInterval + cleanup, same shape as ui/Clock.tsx and
  QuantumRandomWidget.tsx) drives `now`, which feeds a memoized
  `nextTimedEntry` (soonest future timed entry) rendered as one line:
  "NEXT <TYPE>  T-MINUS HH:MM:SS" (or "T-MINUS ND HH:MM:SS" past 24h).
  Renders only when a timed entry exists — zero footprint otherwise.
- A due-alert effect scans timed entries each tick; when one crosses its due
  moment (within a 5-minute trailing window, to avoid mass-firing stale
  alerts on a cold remount), it creates a `calendar_alert` log exactly once.
  Double-guarded: an in-memory Set ref for same-mount re-renders, plus a
  check against already-persisted logs (by a deterministic entryKey) for
  cross-remount safety — same dedup shape already used in RecipeWidget.tsx's
  auto-log effect.
- intentionEngine.ts: added recordCalendarAlertSignal(entryType, date, time),
  a thin wrapper on recordSignal('log', 'calendar_alert', ...) — companion to
  the existing recordCalendarSignal, feeding the same Temporal Planner /
  Pattern 26 surface with the alert-fired half of the loop.
- Logs.tsx: calendar_entry handler now also prints the time when present.
  New calendar_alert handler renders `Block label="ALRT:"` with
  labelClassName="text-red blink" (reusing the existing .blink keyframe
  already used for AdminUser.tsx's active-edit state) — military cockpit
  format, all-caps, data rows only, no prose. This is the "stylish
  military-grade notification": a red, softly-blinking terminal alert block
  in the Log feed, not a browser Notification popup (none exists in this
  codebase; would have been a new, heavier dependency for a feature the
  in-app Log already serves).
