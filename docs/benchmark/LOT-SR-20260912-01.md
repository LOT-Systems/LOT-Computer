01B // WHAT SHIPPED
--------------------------------------------------------------------------------
TIME TRACKING
  - CalendarEntry gained an optional `time` (HH:mm) field. Add-entry form now
    has a paired <input type="time"> next to the existing text field.
  - Entries sort by date then time; day-view and upcoming-list rows show the
    time inline (tabular-nums, de-emphasized) when set.

ALERT ENGINE (classifyAlert)
  - Per entry, compares scheduled date+time against a live clock ticking
    every 30s (mirrors EvolutionMilestoneToast's poll cadence):
      T-15    entry due within the next 15 minutes
      DUE     entry time has passed, within the last 30 minutes
      OVERDUE entry time passed 30min–12h ago
      TODAY   entry has no time, scheduled today (all-day reminder)
  - Active alerts render as a compact banner directly in the widget, in the
    repo's established terminal-grid vocabulary (font-mono, uppercase,
    tracking-widest, bracketed tier tag) — OVERDUE in red, DUE pulsing,
    T-15/TODAY dimmed. Visible whether or not the calendar panel is expanded.

LOG INTEGRATION
  - Each alert tier-crossing (deduped by localStorage key
    `lot_calendar_alerts_fired_v1`, 7-day pruned retention, so a tier fires
    into the Log exactly once) calls createLog with a new event:
    `calendar_alert` { date, time, entryType, text, tier }.
  - New recordCalendarAlertSignal() added beside the existing
    recordCalendarSignal() in intentionEngine.ts — feeds the same 'log'
    signal channel other calendar signals use.
  - Logs.tsx gained an `ALERT:` military handler for `calendar_alert`
    (mirrors the existing `CAL:` handler for calendar_entry), and the CAL:
    handler itself now also prints time when the entry has one.
