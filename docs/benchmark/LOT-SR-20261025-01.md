Observations:
- **No widget is lazy-loaded.** All `*Widget` modules are statically imported into `System.tsx`; `dist/client/js/app.js` = 730 KB raw / 185 KB gzip, `about.js` = 442 KB / 131 KB gzip (`About.tsx` 4,889 lines, `Logs.tsx` 4,506).
- **`SystemProgressWidget.tsx` is 2,513 lines** (mostly changelog data) and `intentionEngine.ts` is 6,504 lines with pattern analysis running synchronously in one function. Prime candidates for splitting/lazy data.
- 16 widgets consume `useLogs`; shared cache (5 min stale, 500 row server cap) keeps this to one request. The comment in `queries.ts` still says "no LIMIT" (stale; the server limits to 500).
- Polling: stats queries refetch every 120 s with `refetchIntervalInBackground: false` (good). Intervals **without** a visibility guard: `QuantumRandomWidget` (1 s tick + 10 s toggle), `MicroCalculatorWidget` (10 s). `MicroGameWidget` is viewport-gated via `useInViewport` and has a pause ref.
- Error containment: `WidgetErrorBoundary` wraps the main groups in `System.tsx` (51 references), but F1/F2 show a throw inside the shared engine bypasses per-widget isolation when it occurs in a `useMemo` of a widget outside a boundary.
- `React.memo` used in 1 of 39 widgets; every `intentionEngine` write re-renders all subscribers (mitigated in a few widgets by memoising on `engineState.signals`).

## C. Wiring

**Widgets → LOT® Quantum Intent Engine (QIE).** 21 of 39 widgets emit signals via `recordSignal`/`record*Signal`; signals are capped at 1,000 (`MAX_SIGNALS`) and persisted to localStorage on a coalesced deferred write. Widgets that read logs but **emit nothing**: AIFeedback, Benchmark, Evolution, Integrity, InterfaceEvolution, QuantumSign, QuantumState, SignalStream, SystemPulse. These are display-only: acceptable by the "container vs display" model, but QuantumSign is interactive and is a candidate to emit.

**QIE → System tab.** `System.tsx` consumes `getOptimalWidget`, `getUserIndex`, `classifyPhysiologicalCohort`, circadian phase and astrology signal (once per day, now with a 15-min off-tab-paused recompute). Wiring is live; F1 was the main break.

**Memory / Story.** `MemoryWidget` posts answers (`answer` log event) and feeds signals; narrative and Story consumers read logs via `useLogContext`. One type gap remains: `MemoryWidget.onSuccess` destructures `insight` which the mutation type does not declare (runtime-safe, untyped).

**LOT® AI.** Memory/AI engine status is derived server-side from tags + provider keys in `useProfileView`. Not exercised here: no provider keys in this environment.

**Portrait (profile page).** `PublicProfile.tsx` (673 lines) and `About.tsx` are separate bundles; Portrait reads logs/metadata, not the live QIE store. Remaining profile type debt: `UserProfile.metadata` is read in `app.tsx`/`us.tsx` but absent from the shared type (6 TS errors).

## G. Widget usage data log

What exists: log `event` types written from widgets include `answer`, `emotional_checkin`, `plan_set`, `self_care_complete`/`skip`, `intention`, `calendar_entry`, `report_generated`, `health_check`. `useLogContext` already computes per-user widget diversity, most/least used and dormant modules. **Gap:** this is per-user and client-side; there is no platform-wide aggregate of widget usage across LOT® Systems, and widgets that only emit QIE signals (not log events) leave no server-side trace. Recommended: a daily server rollup (event type × count × distinct users) written to a table, surfaced in the Benchmark widget.
