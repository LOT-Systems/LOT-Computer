02 // DEFECTS FIXED IN THIS PUSH
--------------------------------------------------------------------------------
D1  CRITICAL  intentionEngine.ts — `dayMs` undeclared in Pattern 147
    analyzeIntentions() referenced an undefined `dayMs` (tsc TS2304). Once P142
    and P137 were both active the function threw ReferenceError, aborting the
    entire pattern pass (P147+ never evaluated, callers on mount/idle failed).
    FIX: declared `const dayMs = 24*60*60*1000` at the use site.

D2  HIGH      intentionEngine.ts — QIE -> server sync duplicated and dropped data
    This is the pipe that feeds LOT AI, Portrait, Memory and Story
    (POST /api/quantum-intent/sync -> Log rows `quantum_intent_signal` +
    user.metadata.quantumIntentState/Patterns).
    a) lastSyncedTimestamp was not persisted. After every page load it reset to
       0, so up to 1000 signals (7-day window) were re-uploaded and the server
       (bulkCreate, no dedupe) stored duplicates. This inflates widget-usage
       counts, pattern firings (scheduled-jobs.ts counts these) and Memory
       question context.
    b) After the await, the store was overwritten from a stale pre-request
       snapshot, discarding any signal recorded while the request was in flight.
    c) Trigger was `signals.length % 10 === 0`. Total length is pruned by the
       7-day window / 1000 cap, so exact multiples rarely coincide with an
       elapsed 5-min cooldown; low-volume users could go indefinitely unsynced.
    d) forceSyncToServer() zeroed the watermark (would re-upload everything) and
       was never called anywhere; nothing flushed on tab close.
    FIX: watermark persisted (localStorage `intention-last-synced`) and restored
    on load; watermark = newest uploaded signal timestamp; store re-read after
    await; trigger = unsynced count >= 10 AND cooldown; flush on
    visibilitychange->hidden; forceSyncToServer(force) bypasses cooldown only.
    CAVEAT: rows already duplicated on the server are NOT cleaned here. A
    one-off dedupe on (userId, metadata.timestamp, metadata.signal) is advised.

D3  MEDIUM    System.tsx — 6 heavy widgets shipped in the initial bundle
    See §3. FIX: React.lazy + Suspense (empty fallback) for SystemProgressWidget,
    ArchitectWidget, QuantumEngineWidgets, MicroGameWidget, IntegrityWidget,
    PatternRecognitionWidget. Each remains inside its WidgetErrorBoundary.
    Side effect: these render after their chunk loads (below-the-fold, so
    expected layout shift is small but non-zero — verify on device).

06 // DATA STORING AND USAGE LOG
--------------------------------------------------------------------------------
Data lives in three places, none with a unified widget-usage record:
  1. localStorage (per device): intention-signals, intention-last-synced (new),
     user-index, intentions-last-shown, subscribe-clicked, widget flags.
  2. Postgres Log table: quantum_intent_signal, calendar_entry, plan_set,
     self_care_complete/skip, health_check, report_generated, emotional
     check-ins, memory answers.
  3. user.metadata JSON: quantumIntentState / Patterns / SignalCount.
GAP: there is no "platform-wide widget usage log". The closest source is
Log where event='quantum_intent_signal' grouped by metadata.source, which only
covers the 17 signalling widgets and (before D2) was duplicated.
PROPOSAL: reuse recordSignal with a `widget_view`/`widget_action` signal from a
shared hook in WidgetErrorBoundary (one place, all widgets), then aggregate
server-side in an admin report. Impressions must be sampled and dedup'd per
session to avoid Log table growth (/api/logs already caps at LIMIT 500).

07 // 15-MONTH REVEAL AUDIT
--------------------------------------------------------------------------------
FINDING: No month-based reveal schedule exists in code. interfaceEvolution.ts
gates features by `featureUnlockLevel` (0–5) computed from behavior, and
MonthlyPulseWidget shows "Month N/12" for Usership. System.tsx mounts nearly
every widget unconditionally (exceptions: Intentions cooldown, Subscribe 20%
random, Investor stack behind a setting, Architect paid-only).
Consequence: a day-1 user gets the full stack; the "month-to-month build-up"
is not enforced, and the reveal is 12 months in one place and 5 levels in
another, not 15 months.
PROPOSAL (needs S-2 decisions): a single REVEAL_SCHEDULE map
  month -> [widget ids], read by System.tsx via one `isRevealed(id)` helper,
  driven by account age with the level gate as an early-unlock. Draft grouping:
  M0–1 Time, Log, Memory, Mood, Weather · M2–3 Planner, Calendar, Recipe,
  Intentions, MonthlyPulse · M4–6 Narrative, GoalJourney, Chakra, Cohort,
  PatternInsights · M7–9 QIE widgets, Biofield engine, Evolution · M10–12
  SystemProgress, UserMetrics, CorrelatedIndexes · M13–15 Architect, Investor,
  Benchmark, CosmicUpdate. Not implemented: it changes what every user sees.

08 // MONK / SELF-CARE LOG POSTING (design, not built)
--------------------------------------------------------------------------------
Idea: any interactive widget can post a synchronized context line to the Log
in a fixed SITREP format, e.g.
  0645Z | SKY CLEAR 14C | 212 ONLINE | PLANNER SET 3 | STATE: CALM
built from stores already available (weather, usersOnline, time, userState).
Fits existing plumbing: Log(event) + getLogContext already snapshots weather
and time server-side, so the client only needs to send widget + action + note.
Guard rails: opt-in per widget, one line per action, no free-text echo of
private fields, and LOT AI reads them as "discipline" context (streaks,
consistent rise/rest) — consistent with the monk-and-transparency brief.
Not built: requires S-2 sign-off on line grammar and privacy scope.
