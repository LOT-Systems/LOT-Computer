DELIBERATE BOUNDARY — WHY ON_STRENGTH IS NOT SELF-SERVICE:
  User.canEditTags() restricts tag mutation to the CEO account for a reason:
  a tag is how this codebase gates paid access (Usership, Admin, Suspended
  all work this way). Granting 'Basic' is granting a paid physical-ration
  subscription. No payment processor is wired in this codebase today
  (stripeCustomerId exists on the User model as a placeholder column; no
  Stripe SDK call, checkout flow, or webhook exists anywhere in the repo).
  Building a self-service path straight from PENDING to ON_STRENGTH would
  therefore mean either (a) a user can grant themselves free paid access —
  a real privilege-escalation bug, not a feature — or (b) fabricating a
  billing charge that never happened, which the directive's own cardinal
  rule ("Honest engineering... do not fabricate") rules out directly. So
  PENDING -> ON_STRENGTH is a new CEO-gated endpoint (/api/basics/confirm,
  guarded by the same canEditTags() check as the existing tag-edit route)
  standing in for "payment confirmed, issue authorized" until a real
  processor lands. This is the one piece of the M2 exit criterion — "a
  Usership member can go ON STRENGTH and back OFF, end to end" — that is
  operator-gated rather than fully self-service, and it should stay that
  way until Month 2's billing work is actually done, not simulated.
