06 // LOG ENTRY SYSTEM — CURRENT STATE (audit findings)
--------------------------------------------------------------------------------
The Log/Journal system S-2 described is not a proposal — it is a running
system, built across many prior sessions (earliest slash-command wiring:
SR ledger 20260614 "LOG Terminals v56"; /system + /story bug-fixed as far
back as ledger line 20260622-01). This session verified each described
piece against the live code rather than re-implementing it:

CONTEXT SNAPSHOT (item 1 — weather/time/humidity/sky/location/astrology)
  Real, server-side, automatic. `getLogContext()` (src/server/utils/logs.ts)
  builds { temperature, humidity, weatherDescription, country, city,
  timeZone, date, astroRokuyo, astroMoonPhase, astroMoonIllumination,
  astroHourlyZodiac, astroWesternZodiac } and is attached to every Log row
  at creation — not just journal text, any log-like event (memory answers,
  prayer, story, recipe). There is no separate "click a widget to snapshot"
  UI; the snapshot is implicit in "any record creation," which is the
  functional equivalent S-2 described. `Logs.tsx`'s `system_snapshot` event
  case is the one place this renders back to the user directly.

PASSIVE JOURNAL + FOLLOW-UP (item 2)
  The primary `NoteEditor` in Logs.tsx is exactly this: free-text entry,
  autosaved, no forced prompts. Follow-up-on-spike is handled by a
  separate, much larger subsystem (Memory Engine / QIE pattern library,
  100+ named patterns e.g. RECOVERY PLATEAU, SIGNAL BURST) that reads the
  same Log rows independently. That system predates and exceeds the ask;
  not touched this session.

COMPRESSED STORY (item 3 + logic chain)
  `/story` (`POST /api/story`, api.ts ~5486-5620) already implements the
  described chain: LOT User data (last 200 logs, filtered to moods/
  entries/self-care) -> Quantum Intent Engine (`quantumState`/`userIndex`
  computed client-side by intentionEngine.ts, sent in the request body)
  -> AI vendor processor (`aiEngineManager.getEngine('together')`,
  src/server/utils/ai-engines.ts) -> stored back as a `generated_story` Log
  row (personalized data stored). Gated on Usership tag. A separate
  Sunday-automated ROUTINE 1 (LOT-MANIFEST.md §06) already runs a weekly
  version of the same compression server-side without a session.
  THIS SESSION'S CHANGE: the /story prompt built RECENT MOODS / RECENT LOG
  ENTRIES / SELF-CARE DATA blocks but never read the context snapshot
  already sitting on `req.user` at call time — weather, astrology, location
  were captured and stored but never made it back into the narrative. Added
  an ENVIRONMENT SNAPSHOT block (reusing the same `getLogContext()` call,
  one fetch, no new DB load) and one explicit prompt rule: use it as
  optional texture, at most one detail, never lead with it, never force it.
  This was a deliberate constraint — S-2's vision is a personal story, not
  a weather report; the environment data earns a place in the sentence only
  when it fits the mood the actual log data establishes.

SLASH COMMANDS (item 3 — /system, /story)
  `src/client/utils/logTriggers.ts` — pure `detectTriggers()`/
  `detectNewTriggers()` over a `RULES` table; 17 triggers including
  `system-help` (/system) and `story-mode` (/story, also 📖). Wired in
  `Logs.tsx`'s `NoteEditor` keystroke effect (~3934-4169). /system prints
  the full live command list (verified accurate against RULES — all 17
  triggers present, nothing orphaned). /story strips the trigger text,
  calls the route above, and appends the returned story back into the log.
  Both confirmed working end-to-end by static trace; no server available
  in this container to exercise the HTTP path live (DB not provisioned),
  so this is a build+read-path verification, not a runtime smoke test —
  flagged honestly rather than claimed as tested.

ARCADE / GAMIFIED EVOLUTION (S-2's explicit note)
  Real and large, not a stub: `src/client/utils/badges.ts` is 8,149 lines,
  hundreds of badges across 20+ "Word Turn" engines (keyword-in-journal
  detectors), calendar/behavioral easter eggs, and RPG-style achievement
  tiers up to "cosmic" rarity, entirely client-side and already driven by
  the same Log rows the Journal writes. Two pre-existing duplicate object
  keys (`quarter_drop`, `elixir_found`) surfaced as esbuild warnings during
  CHECK A/B — cosmetic (last definition wins, no runtime break) and outside
  this session's scope; noted for a future badge-hygiene pass rather than
  fixed opportunistically here, since a comparison of the two definitions
  showed different rarity/description values and picking the wrong one to
  delete silently changes player-facing text — that decision belongs to
  whoever owns the badge corpus, not a drive-by fix. No command-usage badge
  exists yet (typing /system or /story does not itself award anything);
  flagged as a natural next hook, not built here — the existing 8k-line
  registry did not need a hurried addition on top.

QUANTUM INTENT ENGINE -> AI VENDOR (proposed logic chain)
  Confirmed as built, with a naming note: "QIE" in the codebase is the
  client-side heuristic signal/pattern classifier (intentionEngine.ts —
  patterns, archetypes, cohort classification), not itself an LLM caller.
  The AI vendor call is a separate abstraction (`ai-engines.ts`,
  `AIEngineManager`, 6 providers, Together AI primary with automatic
  fallback). The chain S-2 described — LOT User data -> QIE -> AI vendor
  -> personalized data stored — is real; QIE's role is producing the
  `quantumState`/`userIndex` summary that seeds the AI prompt, not
  executing the AI call itself.

MORNING QUESTION (S-2's device/widget ask)
  Exists as two separate mechanisms, not one: `ContextualPromptsWidget`
  (client heuristic, `timePhase === 'morning'`) and the Memory Engine's
  daily prompt-pacing quota (src/server/utils/memory.ts, ensures at least
  a morning and a night question per day). No unified "LOT personal
  computer device" morning ping found in this repo — likely out of this
  codebase's scope (hardware/companion-app territory) rather than missing.

New doctrine clause folded into LOT-DOCTRINE.md:

  ## Environment-As-Texture (/story context weaving)

  A context snapshot (weather/astrology/location) exists on every Log row
  via getLogContext() whether or not the consuming feature reads it. When
  wiring a new AI-narrative route, fetch it once at the top of the handler
  and reuse the same value for both the prompt and the row's own `context`
  field — do not call getLogContext() twice per request. Feed it to the
  model as optional texture with an explicit "at most one detail, only if
  it fits" instruction, never as required content: the operator's actual
  log/mood/self-care data is the subject; environment is set dressing. A
  narrative feature that leads with the weather has inverted the priority.
