05 // ROUTINES IMPLEMENTED (this session)
--------------------------------------------------------------------------------
R1 TIME TRACKING     CalendarEntry gained `time: string | null`. Add-entry form
                     gained a native <input type="time"> beside the text field
                     (optional — omitting it keeps the old all-day behavior).
                     Stored in Log metadata.time and folded into the existing
                     "[SCHEDULE] type: text (date)" log line as "at HH:mm" when
                     present. Entry lists (day view + upcoming) now print the
                     time inline at 40% opacity, ahead of the entry text —
                     opacity hierarchy per doctrine (metadata < primary text).
R2 DUE-LIST RELIABILITY  Upcoming list previously kept every entry with
                     date >= today, so a timed entry sat in the list all day
                     after it had already passed. Now: today's entries with a
                     time are dropped once that time is behind now (dayjs
                     isAfter check); date-only entries and future dates are
                     unaffected. Cause: filter only compared dates, never time.
R3 STATE-LEAK FIX    Clicking a second date while the add-entry form was open
                     left entryText/isAddingEntry bound to the old date — the
                     Add button would silently write the new text under the
                     date you'd already left. handleDateClick now resets
                     isAddingEntry/entryText/entryTime whenever the selection
                     moves to a different date (deselecting the same date is
                     untouched).
R4 OPS-ALERT NOTIFICATION  New CalendarEventNotification.tsx. Polls useLogs
                     every 20s (only while tab visible and system route
                     active, matching the existing EvolutionMilestoneToast
                     gating pattern) for a calendar_entry whose date+time has
                     just arrived (due, and still within a 15-minute recency
                     window so a backgrounded tab doesn't dump a stale
                     backlog on wake). Fires once per entry — a fired-key set
                     (date|time|type|text) is kept in localStorage, capped at
                     200, purely to dedupe across polls within a session; the
                     entry of record stays in Log/Postgres, not localStorage.
                     Style: fixed top-right card, acc/20 border, grid-fill-light
                     background (same texture token as the milestone toast),
                     uppercase "SCHEDULE // DUE" + entry TYPE readout, 8s
                     fade — an ops-readout register distinct from the
                     milestone toast's centered/glowing one, no color, no
                     emoji, periods over checkmarks. No OS push, no sound —
                     consistent with the documented "Context Over Notification:
                     no push, no alert, no interruption" directive; this is an
                     in-app surfacing at the moment the operator is already
                     looking at the system, not an interruption.
R5 WIRING            Mounted <CalendarEventNotification /> in System.tsx next
                     to <CalendarWidget />, each in its own WidgetErrorBoundary
                     so a fault in the alert never takes the calendar grid
                     down with it (or vice versa).
