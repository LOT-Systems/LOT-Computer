05a // CHANGE DETAIL
--------------------------------------------------------------------------------
src/client/utils/logTriggers.ts:
  Added parseStoryPeriod(text) -> 'day'|'week'|'month'|'year'. Pure function,
  no store/DOM access, consistent with the module's existing detector style.
  Matches "/story <period>"; defaults to 'day' when no period token or an
  unrecognized one follows.

src/client/components/Logs.tsx:
  story-mode trigger handler now calls parseStoryPeriod(value) and sends
  { logText, period, quantumState, userIndex } to submitStory instead of
  always omitting period. logText strip regex extended to also eat the
  period token so it doesn't leak into the free-text sent to the engine.
  /system help block: "/story" line split into four lines (bare/week/month/
  year) so the period syntax is discoverable without reading source.
  Added a `generated_story` render case in the past-logs list (STORY: label,
  period shown in brackets) — previously generated stories rendered as
  nothing once pushed out of the primary slot; they were being silently
  erased from the visible Log the same way the DOCTRINE's Widget->Memory
  Compression Loop clause warns an unhandled event type is silently erased
  from the Memory Engine's prompt. Same failure class, different consumer.

src/client/queries.ts:
  useStoryGeneration mutation body type gained `period?`; response type
  gained `period` (server always echoes the resolved period back).

src/server/routes/api.ts (POST /story):
  - Body now accepts `period`; resolved against STORY_PERIOD_WINDOWS
    (day=1, week=7, month=30, year=365 days), invalid/absent -> 'day'.
  - Log query changed from `limit: 200` over all history to
    `createdAt >= now - windowDays` (Op.gte) over `limit: 500` — the story
    is now actually bounded to the period it claims to summarize.
  - STORY-LOOP: looks up the operator's most recent generated_story Log; if
    its metadata.period matches the period just requested, its stored story
    text is injected into the prompt as "PRIOR COMPRESSED STORY" and the
    system prompt instructs the engine to build on it and compress further
    rather than re-derive the person from scratch each call. Cross-period
    rows are never fed forward (a month story must not compress into a day
    story) — full detail in DOCTRINE (STORY-LOOP).
  - Prompt also now explicitly instructs the engine to surface real high
    and low peaks of the period rather than flattening to one mood, per
    the S-2 spec's "surface more intimate high and low peaks."
  - Stored Log metadata gained `period` and `compressedFrom` (prior story's
    Log id, or null) — the compression chain is walkable without touching
    the append-only ledger convention.
  - Response gained `period` field (client already updated to read it).
  - Full doctrine writeup: docs/benchmark/LOT-DOCTRINE.md, "Story Command
    Period Compression (STORY-LOOP)".
