05 // ROUTINES IMPLEMENTED (this session)
--------------------------------------------------------------------------------
R1 TIME-ON-ENTRY     CalendarEntry gained an optional `time` (HH:mm) field.
                     Add-entry form gained a native <input type="time">
                     alongside the text field; stored in calendar_entry log
                     metadata.time. Entries with no time keep working exactly
                     as before (date-only, all-day).

R2 DATETIME ORDERING entryDateTime(entry) combines date+time (or midnight when
                     time is absent) into a single dayjs instant. Entries list
                     and upcoming list now sort/filter on that instant instead
                     of the raw date string, so same-day timed entries order
                     correctly and a timed entry drops off "upcoming" the
                     moment it passes rather than staying all day.

R3 COUNTDOWN         Upcoming entries show entryDateTime(entry).fromNow() next
                     to the date/time (dayjs relativeTime plugin, already
                     loaded in #client/utils/dayjs — no new dependency).

R4 DUE-ALERT ENGINE  New effect in CalendarWidget polls every 30s (paused on
                     hidden tab) for timed entries whose instant has arrived
                     and is within a 10-minute window, not already notified.
                     Fire-once guarantee: notified entries are keyed
                     (date|time|text) into a capped (500) localStorage set,
                     read on mount and written on every fire — reliable across
                     reloads/remounts, no repeat alerts, no server schema
                     change needed.

R5 MILITARY-STYLE    New toast: fixed bottom-center, bordered box, grid-fill
   ALERT TOAST        texture, "// SCHEDULE ALERT //" tracked-uppercase header,
                     uppercase entry type, entry text, time — matches the
                     existing EvolutionMilestoneToast chrome exactly (same
                     fade-in-up/fade-out keyframe shape, renamed to avoid
                     collision) so it reads as native chrome, not a new UI
                     idiom. No new colors — text-acc only, minimalist.

R6 ALERT -> LOG       Each fired alert also POSTs a calendar_alert log
                     (event: 'calendar_alert', metadata: date/time/entryType/
                     text) — the notification itself has its own trail in the
                     Log feed, separate from the original calendar_entry.

R7 LOG FEED HANDLERS Logs.tsx CAL: block now also prints the entry text (was
                     type + date only) and the time when present. New ALERT:
                     block renders calendar_alert entries in the same tactical
                     idiom (Block label, uppercase, tabular-nums).

R8 TEMPORAL PLANNER  System.tsx's "Next:" surface (the separate Temporal
                     Planner memo that shows the nearest calendar_entry above
                     the widget stack) now also prints the time when the
                     entry has one — kept in sync with the widget so both
                     surfaces agree.
