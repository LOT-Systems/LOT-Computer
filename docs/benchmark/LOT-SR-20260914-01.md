DESIGN NOTES
--------------------------------------------------------------------------------
TIME TRACKING:  calendar_entry metadata gained an optional `time` (HH:MM)
  field via a native <input type="time"> beside the existing text input —
  entries stay pure date reminders when time is left blank, so all existing
  data and behavior is untouched. A 30s internal tick re-renders a
  "TRACKING: <next entry> — <fromNow()>" line above the upcoming list,
  giving the widget a live countdown without polling the server.

ALERT MATCH:  calendarAlerts.ts is a pure, dependency-free matcher —
  findDueCalendarEntry(logs, now) walks calendar_entry logs, combines
  date+time into a dayjs instant, and returns the first entry whose due
  time has passed but is still inside a 3-minute grace window and hasn't
  already fired (localStorage-backed fired-id set, capped at 200). The
  grace window is what makes this "reliable" rather than noisy: an entry
  from before this feature existed, or a due time missed because the tab
  was closed, never retroactively alerts — it simply has no time-tracking
  countdown, same as today.

MILITARY-GRADE NOTIFICATION:  CalendarAlertToast mirrors the existing
  EvolutionMilestoneToast pattern (interval + document.hidden/isRouteActive
  guard, one-shot fire, CSS keyframe in/out) but at bottom-right instead of
  bottom-center, in font-mono, with a blinking status dot, a "CAL-ALERT"
  bracket-code header, uppercase-tracking-widest entry type, tabular-nums
  date/time, and an "ACK" dismiss control — the same terse, bracket-coded,
  opacity-tiered terminal vocabulary already established across Logs.tsx's
  90+ event handlers (CAL:, MULTI:, QOS-COHR:, etc.), not a new aesthetic.

LOG WIRING:  the alert also writes a calendar_alert Log event (best-effort,
  same createLog + refetchQueries + try/catch-signal pattern CalendarWidget
  already uses for calendar_entry), so the notification leaves a durable
  record in the field archive, not just a transient popup. That required
  three small consistency additions beyond the widget itself: the
  displayableEvents whitelist in routes/api.ts (events not on this list are
  silently dropped by GET /logs — confirmed via /docs/benchmark/ ledger
  history of "displayableEvents gap" fixes), CALENDAR_EVENTS in
  scheduled-jobs.ts, and the calendar_alert -> 'calendar' row in
  selfAssembly.ts's dependency map.
