This was a scheduled/autonomous run with no S-2 present to answer questions in
real time (per the LOT-BENCHMARK protocol's own boundary: "intake and
classification is judgment, not mechanism — keep S-2 in view there"). The
LOT-FM-001 directive's Month 3 scope is REAL FULFILLMENT: confirmed supplier
quotes against a hard COGS ceiling, a printed manifest card, and shipping a
physical box to a real subscriber who has been billed real money each month.

Two things this build deliberately does NOT do, and should not do without
S-2 sign-off first:
  1. NO REAL BILLING. grep of the full repo found zero payment-processor
     integration (no Stripe, no charge/webhook code — only a dead unused
     `stripeCustomerId` column). "USD 100.00/MO" is displayed and the roster
     state machine tracks enrollment, but no money moves. Wiring a real
     payment rail is a business decision (which processor, PCI posture,
     refund/dispute handling) that belongs to S-2, not to an unattended run.
  2. NO REAL SHIPPING. The issue log this session writes is SCHEDULED only —
     never DISPATCHED. Actually procuring 23 SKUs under a $40 landed
     ceiling, confirming supplier quotes, and mailing a box to a real person
     is a physical-world commitment (money spent, an address used, a
     customer expectation set) that this session has no way to verify safely
     end-to-end and should not fake or half-wire.

Recommendation: M3 should start with S-2 confirming (a) a payment processor
decision and (b) actual supplier quotes in hand, before any code assumes a
real charge or a real dispatched box. Everything M3 needs on the software
side — enrollment state, cadence dates, an issue-log row waiting to flip from
SCHEDULED to DISPATCHED — is now in place and ready for that wiring.
