## 4. Synchronized context in the Log ("military comms" line)

Server `getLogContext` already stamps each log with: weather (temp, humidity, description — cached 30 min), city/country/timezone, local date-time, and ambient astrology (rokuyo, moon, zodiac hour/sign).
**Gap:** *users online* was in the System tab but not in the log context.
**Fixed:** `usersOnline` added to `LogContext` via a 30-second cached snapshot (§6.3), so every log line now carries the same ambient frame the user saw: *time · weather · users online*.

## 5. 15-month reveal

- No calendar-driven 15-month schedule exists in code. The interface "reveal" is **achievement/maturity-driven** (`interfaceEvolution.ts`: maturity thresholds 25/50/75/95%, story chapters at levels 10/30/60), plus `MonthlyPulseWidget`, the only month-indexed element.
- `MonthlyPulseWidget` was **capped at 12 months** (messages 1–12, label and "N / 12" hard-coded) — mismatch with the 15-month program.
- **Fixed:** cap raised to 15, with messages for months 13–15. **Copy for 13–15 is placeholder — owner should review wording.**
- Not done (design decision needed): a true month 1→15 unlock table mapping each month to specific widgets. Currently Month 3 "Active User" is only a message, not a gate. Pulse dismissal is per-browser (`localStorage`), so it re-shows on another device.

## 6. Changes in this push

1. **`intentionEngine.ts` `syncToServer` (real bug).** After the POST, the code wrote back the *pre-request* state snapshot and stamped `lastSyncedTimestamp = now`. Any signal or pattern recorded while the request was in flight was overwritten in the store, and signals timestamped before `now` but after the snapshot were skipped on the next sync. Now merges into the current store state and advances the watermark to the newest signal actually sent.
2. **`MonthlyPulseWidget.tsx`:** 12 → 15 month cap (`MAX_MONTH`).
3. **`utils/logs.ts` + `shared/types`:** `usersOnline` in log context, 30 s cache, failure-tolerant (falls back to last value).

## 7. Usage data log

- Today there is **no widget-view/usage telemetry**. Usage is inferred from QIE signals, which are (a) retained client-side for only **7 days** (`SIGNAL_RETENTION`), (b) capped at 1000, (c) synced to the server as `quantum_intent_signal` Log rows (durable, hidden from the user-facing Log).
- So a 15-month widget-usage history is only recoverable from server Log rows, and only for widgets that emit signals (22 components). Display-only widgets leave no trace.
- **Recommendation:** one `widget_view`/`widget_action` signal helper called from `WidgetErrorBoundary` (mount) and from `LazyMount` (first visible), batched through the existing `syncToServer` path; plus a monthly rollup job (there is already `utils/monthly-summary.ts`). This gives a per-widget, per-month usage table without new tables.

## 8. Load speed

- **All ~45 widgets are statically imported into `System.tsx`**; `React.lazy` is used nowhere. `client.build.ts` has `splitting: true`, so converting to `React.lazy` + `Suspense` would yield real chunks at no build-config cost.
- `LazyMount` (viewport-deferred mount) wraps only `QuantumEngineWidgets`. Candidates by size/cost: `SystemProgressWidget` (**2513 lines, 36 data/API references**), `MicroGameWidget` (988), `SelfCareMoments` (869), `QuantumEngineWidgets` (651), `PatternRecognitionWidget` (561), `IntegrityWidget` (476). Below-the-fold stacks (Dashboard, Biofield Engine, Investor, Architect, Calendar, Benchmark) should be lazy **and** `LazyMount`ed.
- Not measured (no build). Bundle size: run `yarn client:js:build:metafile` to get a baseline before/after.
- Existing good practice: deferred persist (`schedulePersist`), `deferHeavy(analyzeIntentions)`, analysis cooldown, atom writes moved out of `useMemo` (documented in `System.tsx`).

## 10. Server notes

- `/quantum-intent/sync` accepts an unbounded `signals` array with no per-field validation (`source`, `signal` strings written straight to `Log.text`). Add a cap (e.g. 500) and string length limits. Sync is also not idempotent — a lost response re-sends the same signals (partly mitigated by the §6.1 watermark fix, not eliminated; dedupe on `(userId, timestamp, signal)` recommended).
- `user.metadata.quantumIntentSignalCount` is incremented by batch size, so it overcounts on retries.

## 11. Monk-lifestyle / transparency check (LOT® AI)

Design intent is supported by what exists: AI-facing outputs are logged (`assembly_directive`, `scheduled_job`, `benchmark_read`), and ambient context is stamped on logs (now including users online). Missing for "pure and transparent": a user-visible record of *which* widget/signal produced each AI insight. Recommendation: include `signalSources` in the insight metadata and show it in the Log line.
