### Alert ladder (T-minus)

```
T-15  ARMED      15 min out
T-05  IMMINENT    5 min out
T-00  ZERO        scheduled minute (pulses)
MISSED            10 min past, not ACK'd/done
```

### Reliability rules

- Ticker: 15 s interval + immediate re-check on tab focus / visibility regain (covers sleeping tabs).
- Only the LATEST reached stage fires — reopening after a gap never bursts stale alerts.
- Alerts older than 120 min past schedule are dropped.
- Never runs backwards: if T-00 (or later) has fired, T-15/T-05 are skipped.
- De-dupe is double-keyed: localStorage (`lot.calendar.fired`, capped 300) AND
  `calendar_alert` logs (`metadata.alertKey`) so a second device/cleared storage does not re-fire.
- Ticker waits for logs to load before firing (no false "unfired" state).
- Past times are rejected at entry ("Time already passed.") instead of silently never alerting.
- Invalid dates (2026-02-31) and times (24:00, 12:60) rejected by engine.
- Date-only (untimed) entries behave exactly as before — no alerts.
- Browser Notification used if permission granted (requested on first timed entry).

### UI (minimal)

- Optional `time` input beside the text field; time shown in lists as `· 14:30`.
- Alert banner above the widget, uppercase tabular line with left rule whose
  intensity rises by stage:
  `T-05 IMMINENT · CALL · 14:30 · T-4m   Dentist      ACK / DONE`
- `✓` on upcoming rows marks done; done entries leave the upcoming list and
  are struck through in the day view.

### Log integration

```
calendar_entry  [SCHEDULE] type: text (date time)        + metadata.time
calendar_alert  [ALERT] T-05 IMMINENT · CALL · 14:30 · … metadata: alertKey, stage, entryId, date, time
calendar_done   [DONE] type: text (date time)            metadata: entryId
```
