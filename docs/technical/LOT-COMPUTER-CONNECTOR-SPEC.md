## 00 — WHAT ALREADY EXISTS (read before building)

The live server already has the two primitives this device needs:

```
1. Log model + Log.create({ userId, event, ... })   src/server/routes/api.ts
   — every user-facing event on lot-systems.com (answers, check-ins,
   plan_set, qi_rfi, badge_unlock...) is one row in this table.

2. GET /logs whitelist (`displayableEvents` array,   src/server/routes/api.ts
   api.ts:1084) — an event type MUST appear in this  :1084
   whitelist or it is silently invisible in the Log
   tab, per doctrine "Backend Whitelist Hygiene"
   (LOT-DOCTRINE.md). This has bitten prior sessions
   (SR-20260604-01: calendar_entry saved but never
   returned) — do not repeat it for hardware events.

3. SSE push channel (`write({ event, data })`,       api.ts:347
   e.g. 'live_message', 'users_online') — an existing
   live server->client push mechanism already running
   in production, which the device's downlink reuses
   the pattern of rather than inventing a new one.
```

The Cube is therefore not a new subsystem — it is a new **client** of the
Log table and a new **subscriber** of the push channel, plus one new
pairing endpoint.

## 01 — PAIRING

```
POST /api/device/pair
Body:  { pairing_code: string, device_type: "cosmo_cube" | "cosmo_cube_mini",
         device_hw_id: string }   (device_hw_id = ESP32 factory MAC, for
                                    duplicate-pairing detection)
Auth:  none (pairing_code is the short-lived secret, generated by the
        LOT web/app UI when the operator starts device setup, shown as
        both text and a QR code for the BLE-provisioning flow)

Response: { device_id: string, device_token: string (JWT, long-lived,
            device-scoped — NOT a user session token), userId: number }
```

`device_token` authenticates all subsequent device calls. It is scoped to
exactly one userId and one device_id — it cannot read or write any other
user's data, and it cannot do anything a normal user session can do beyond
the two endpoints below (no login, no settings changes, no purchases). This
mirrors the existing "S-2 operator token" scoping already described in
LOT-TERMINAL-SYNC.md §Authentication, narrowed further since a physical
object is a higher-loss-risk credential holder than a phone.

## 02 — UPLINK: BUTTON PRESS -> LOG TAB (item 16)

This is the concrete implementation of the brief's "signal back to the
site's Log tab":

```
POST /api/device/event
Auth:  Bearer <device_token>
Body:  { type: "ack" | "sensor" | "online", notification_id?: string,
         sensors?: { temp_c, humidity_pct, pressure_hpa }, ts: ISO8601 }

Server handling (new code, follows the existing pattern exactly):
  await fastify.models.Log.create({
    userId:  <resolved from device_token>,
    event:   'hardware_copy',        // for type: "ack"
    // or event: 'hardware_weather'  // for type: "sensor"
    // or event: 'hardware_online'   // for type: "online" (first boot / re-pair)
    data:    { device_id, ...payload },
  })
```

**Required addition, not optional:** `hardware_copy`, `hardware_weather`,
and `hardware_online` must be added to the `displayableEvents` whitelist at
api.ts:1084 in the same change that adds this route. Skipping this step
reproduces the exact SR-20260604-01 bug (event recorded, never visible) —
this is the single most important implementation note in this document.

Log body content follows COCKPIT-RULE (LOT-LEXICON): instrument readings
only. A Copy-press log entry reads as data, not narration:

```
[HW-COPY]  device: cosmo-cube-0042  notif: mcl_20260920_0731  ack: T+4s
```

not "Vadik acknowledged his coffee reminder." The Log tab's existing
label/body convention already draws that line for every other event type;
hardware events follow the same convention rather than getting a bespoke
prose style.

## 03 — DOWNLINK: SERVER -> DEVICE NOTIFICATION (item 2)

```
Channel:  wss://sync.lot-systems.com/device/<device_id>
          (device-scoped WebSocket, same SSE-derived push pattern already
          live at api.ts:347, extended with a per-device room instead of
          the current global broadcast)

Message:  { notification_id, text: "Coffee time!", pattern_source: "MCL",
            ts }
```

`pattern_source` traces every pushed message back to the QIE pattern (or
background job) that generated it — e.g. `"MCL"` for the existing Job 18
morning-launch-sequence output, `"weather"` for a local weather-driven nudge,
`"manual"` for anything Vadik triggers by hand for testing. This is the
same INTSUM discipline the QI terminal already uses (assessment + source),
applied to a two-word screen message instead of a paragraph — the message is
short, but where it came from is never a mystery.

No new intelligence is proposed here. The QIE already decides *when* to
nudge (existing pattern jobs); this connector only decides *how that nudge
reaches a device screen instead of the web app*.

## 04 — SECURITY NOTES

```
- device_token stored encrypted on-device (NVS encryption, firmware spec §01)
- device_token revocable server-side (lost/stolen device -> operator revokes
  from their LOT Systems settings, same place session tokens are managed)
- No PII in sensor uplinks beyond what BME280/PIR/light already measure
  (room temperature, humidity, pressure, motion boolean, lux) — this is
  the same "environmental/hardware metrics only" boundary already stated
  in LOT-TERMINAL-M2M.md's Data Privacy section, applied to a first-party
  device instead of a third-party S-2 operator's hardware
- Camera (firmware spec §06) never uploads image data — enforced by never
  building an upload path for it, not by a policy toggle that could be
  flipped later
```
