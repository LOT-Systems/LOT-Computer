## INTAKE
```
INPUT   : Scheduled — make Calendar widget reliable; track time; log to Log;
          military-grade notifications; keep minimalist UI.
BASELINE: CalendarWidget stored date-only entries (event calendar_entry).
          No time, no alerts, nothing written to Log on time passing.
```

## BUILD
```
+ src/client/utils/calendarAlerts.ts   pure alert logic (no React/network)
    stages  : WARN  T-15 min | DUE  T-0 (60 min grace) | MISSED (24 h look-back)
    all-day : treated as due 09:00 local
    rule    : each stage fires once per entry; higher stage suppresses lower
    helper  : formatCountdown -> "T-02:15:00" / "T+00:03:10"
~ CalendarWidget.tsx
    optional time input (HH:mm), stored in metadata.time
    15 s tick + visibilitychange re-check (catches sleeping tabs)
    banner: uppercase, left-rule, DUE pulses, ACK dismisses; no extra chrome
    countdown shown on today's rows; "Enable alerts" opt-in for OS notifications
    every fired alert -> createLog(event 'calendar_alert', metadata
      {entryId, stage, entryType, date, time})
    dedupe: localStorage fired-set + fired-set rebuilt from server logs
      (cross-device safe)
~ api.ts   'calendar_alert' added to GET /logs displayable events
~ Logs.tsx CAL-ALERT: renderer (stage · type, date time)
+ scripts/test-calendar-alerts.ts   12-case unit check
```

## KNOWN LIMITS / NEXT
```
- Alerts only fire while the app is open (client-side). True background
  delivery needs a server job or Web Push (service worker + VAPID) — NEXT.
- No edit/delete of entries yet (logs PUT only supports 'note').
- Entries created in other timezones use the viewer's local clock.
- Alert logs are created per viewing device if server logs not yet refetched
  (logs staleTime 5 min); localStorage guard covers same-device duplicates.
- Dependencies installed with --legacy-peer-deps (ERESOLVE on nanostores);
  package-lock not committed.
```
